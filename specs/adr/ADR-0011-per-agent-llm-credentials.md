# ADR-0011：per-agent LLM 憑證，以及它與 P5 的衝突

| | |
|---|---|
| 狀態 | **已採納 (Accepted)** |
| 日期 | 2026-09-26 |
| 決策者 | @architect（依使用者明確需求） |
| 相關 | 修改 [api-contract](../api-contract.md) → v0.5.0；延伸 ZEN-002；**與 P5 有一個必須講清楚的互動**；P1／P2／P3／P4 不受影響 |

## 背景

ZEN-002 給了平台一把全域 LLM 金鑰（`app` 的 `ZENTRA_LLM_API_KEY`），所有 Agent 共用。
使用者要求每個 Agent 能有自己的金鑰，並由平台的資料庫保管，且明確指定了三條行為：

1. 憑證**屬於 Agent**，發新版本不用重新輸入
2. 更新金鑰時，該 Agent 的**所有版本一起變**
3. 要有更新用的 API 端點

## 決定

### 1. 獨立一張表，`agent_id` 當主鍵

```
agent_llm_credentials
  agent_id       UUID PK  → agents.id ON DELETE CASCADE
  ciphertext     text                 -- Fernet token
  last_four      varchar(8)           -- UI 唯一看得到的線索
  base_url       text NULL
  default_model  varchar(128) NULL
  created_at / updated_at
```

**為什麼不是 `agents` 的一個欄位**：`SELECT * FROM agents` 出現在列表、詳情、MCP、
Console 的每一條路徑上。密文放在那裡，任何一次 serializer 改動都可能把它帶出去。
獨立表讓「只有明確去查它的程式碼才碰得到」成為結構事實，而不是紀律。

**`agent_id` 當主鍵直接實現了需求 1 與 2**：版本根本不在鍵裡，所以新版自動繼承；
更新是 `UPDATE` 同一列，所以所有版本立刻一起變。這不是額外寫的邏輯，是資料模型的後果。

### 2. Fernet 靜態加密，未設定就拒絕儲存

金鑰來自 `ZENTRA_SECRET_KEY`。**沒設定時 `PUT` 回 `422`，不接受憑證。**

不退回明文儲存的理由：一個「安全功能在沒設定時靜默降級成不安全」的設計，
比沒有那個功能更糟 —— 使用者會以為金鑰被保護著。

解密失敗（通常表示 `ZENTRA_SECRET_KEY` 被換過）同樣是明確錯誤，
**不靜默退回平台預設金鑰**：那會讓使用者以為自己的金鑰還在用，而帳記在平台頭上。

### 3. 寫得進去，讀不出來

沒有任何端點回傳明文或密文。`GET` 只回 `configured` / `last_four` / `base_url` /
`default_model` / `updated_at`。

服務層也**沒有**回傳明文給 API 層的函式 —— `describe()` 回 metadata，
`resolve()` 只給 Internal Gateway。這是靠「沒有那個函式」保證的。

### 4. Gateway 的選擇順序與稽核

Agent 自己的 → 平台預設。每一列 `llm_calls` 記 `credential_source`（`AGENT` | `PLATFORM`）。

### 5. 刪除 Agent 會硬刪憑證

Agent 是軟刪（`deleted_at`），憑證是硬刪。軟刪是為了保留 metadata 的稽核軌跡，
不是為了讓機密留著。

## ⚠️ 與 P5 的互動（這份 ADR 最重要的一段）

P5 說「Agent 版本不可變」。**憑證是可變的，而且刻意對所有版本生效。** 所以：

> **同一個 `agent@1.0.0`，昨天與今天可能產生不同的結果。**

這在字面上與「版本不可變」有張力。決定是：**接受它，並且定義清楚不可變的是什麼。**

| 不可變（P5 保護的） | 可變（這份 ADR 引入的） |
|---|---|
| 程式碼與相依（image digest） | 用哪一把金鑰 |
| `entrypoints` schema | 打哪個供應商端點 |
| 版本身份（`version_id`） | 預設 model |

**判準是「誰的責任」**：image 是開發者交付的產物，改了就該是新版本；
憑證是維運設定，跟資料庫密碼、TLS 憑證同一類 —— 沒有人會因為換了資料庫密碼而說服務版本變了。

**代價誠實列出**：

- 重現一個舊 Run 的結果，光有 `version_id` 不夠，還要知道當時用的憑證。
  緩解措施是 `llm_calls.credential_source`，但它只分得出「Agent 的」與「平台的」，
  **分不出「Agent 的哪一把」**。要完整可重現就得保留憑證版本史，那是還沒付的成本。
- 換金鑰是一個**沒有灰度、沒有回滾**的動作。一次 `PUT` 之後所有版本立刻改變，
  沒有「先讓 2.0.0 用新金鑰」這種選項。這正是使用者要的行為，但操作上要知道。

## 選項（以及為什麼否決）

### 憑證綁版本（否決）

`agent_versions` 加欄位，或用 `(agent_id, semver)` 當鍵。

- 好處：P5 完全不用讓步，舊版本行為永遠固定。
- **否決理由：使用者明確反對，而且理由成立。** 發新版要重填一次金鑰，
  換金鑰要改 N 次 —— N 隨版本數成長，而且漏改一個就是一個行為不一致的版本。
  這個負擔落在最常做的操作上（發版），換到的是一個很少需要的性質（舊版行為凍結）。

### 金鑰注入沙盒 env（否決）

- **否決理由：直接違反 P4。** 沙盒跑的是使用者程式碼，金鑰一旦進去，
  「程式碼被攻陷」就等於「金鑰洩漏」，而且平台無從知道它被用去做什麼。

### 憑證版本史（延後，不是否決）

保留每次更新的歷史，讓舊 Run 能對回當時用的憑證。

- **延後理由**：它只買到「稽核可重現性」，而在單租戶、內部工具的交付條件下
  （[ADR-0005](ADR-0005-mvp-single-host-scope.md)），還沒有人需要回溯到那個粒度。
  `credential_source` 已經留下最粗的痕跡。真的需要時再做，那時定價也更準。

## 何時該重新檢討

- **出現第二個租戶**：`ZENTRA_SECRET_KEY` 是全平台一把，多租戶下要考慮 per-tenant 金鑰派生。
- **需要稽核級的可重現性**（例如要證明某次輸出是用哪個帳號產生的）：做憑證版本史。
- **金鑰輪替變成常態作業**：現在沒有灰度也沒有回滾，頻繁輪替時這會痛。
- **要接非 OpenAI 相容的供應商**：現在 `base_url` 假設是 OpenAI 相容端點。
