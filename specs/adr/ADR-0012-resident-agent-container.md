## 背景

現在是**一 Run 一沙盒，結束即銷毀**（SPEC §4，ADR-0001 第 2 條）。
使用者問單機能不能承載高併發，實測目前的設定：

| 項目 | 值 |
|---|---|
| 沙盒併發上限 | 10（Redis sorted set） |
| 每沙盒記憶體上限 | 2 GB |
| **允許的總量** | **20 GB** |
| **實測主機可用** | **1.9 GB** |

**超額 25 倍，而且沒有任何地方檢查主機剩餘記憶體** ——
`apps/sandbox/` 裡沒有 `MemTotal`、沒有 `MemFree`、沒有准入控制。
`mem_limit` 是上限不是預留，Docker 不會因為主機沒記憶體而拒絕建立容器。

而 LLM agent 的工作幾乎全是 I/O 等待：實測一次 stock-agent 跑 11.7 秒，
其中約 11.5 秒在等模型回應。那段時間一個 2 GB 的容器完全閒置。

## 決定性的實測（2026-09-27）

**LangGraph 怎麼處理節點的同步／非同步，決定共用容器會不會被一個 Run 卡死。**

```
同步 def 節點（裡面 time.sleep）    3 個並行耗時 1.00s，用到 3 個執行緒
async def 節點（await asyncio.sleep）3 個並行耗時 0.05s，用到 1 個執行緒
async def 節點（裡面 time.sleep）    3 個並行耗時 3.01s  ← 完全序列化
```

判讀，這三個數字改變了這份 ADR 的結論：

1. **`def` 節點是安全的。** LangGraph 把它丟到執行緒池，阻塞不會卡住 event loop。
   這與直覺相反 —— 大多數人會以為「沒寫 async 就會卡死」。
2. **危險的是 `async def` 裡做阻塞呼叫**（`requests`、`time.sleep`、同步 DB driver）。
   那會讓同容器裡**所有**進行中的 Run 一起停。
3. 所以風險**不是「使用者沒寫非同步」**，而是「使用者寫了 `async def` 卻在裡面阻塞」——
   一個具體、可檢測、可以寫進文件的錯誤，不是一個瀰漫性的隱憂。

## 選項

### 選項 A：維持一 Run 一沙盒，只補記憶體准入控制

- 做法：建立沙盒前查主機剩餘記憶體，不夠回 `QUOTA_EXCEEDED`。
- **好處**：ADR-0001 一個字不動。改動最小（Sandbox Manager 多一次檢查）。
- **代價**：**它讓系統誠實，但不讓它更快。** 在 1.9 GB 的主機上，
  誠實的答案是「同時只能跑 0 個」。高併發的問題原封不動。
- 適用：當前提是「跑不可信的程式碼」時，這是唯一選項 —— 隔離不能讓。

### 選項 B：一 Agent 一常駐容器（使用者提案）

- 做法：Agent 發布後可「啟動」，該 Agent 得到一個常駐容器；
  之後所有 Run 都派進那個容器，非同步並行處理。
- **好處**：
  - 記憶體從「並發數 × 2 GB」變成「**啟動中的 Agent 數 × 2 GB**」，有界且可預測
  - 冷啟只付一次
  - I/O 等待被多工掉 —— 這正是 LLM agent 的主要成本
- **代價**（逐項，不含糊）：
  - **Run 之間的隔離從核心保證變成程式碼自律。** `/workspace` 共用，
    全域變數跨 Run 殘留，一個 Run 崩潰帶走同容器所有進行中的 Run。
  - **15 分鐘上限失去強制手段。** 現在逾時是銷毀容器；共用容器要靠行程內取消，
    而 Python 對 CPU-bound 或阻塞的程式碼做不到可靠取消。
  - **資源上限變成 per-agent。** 一個失控的 Run 吃掉整個 2 GB，殺死它的兄弟。
  - 容器掛掉 = 該 Agent 全部不可用，需要重啟機制與健康檢查（新的維運面）。

### 選項 C：常駐容器 + 每容器並發上限 + 溢出開新容器（建議）

```
agent-X  容器 #1   ← 最多同時 N 個 Run
agent-X  容器 #2   ← 第 N+1 個開始放這裡
```

- **好處**：B 的全部，加上**爆炸半徑有界** —— 一個容器掛掉影響 ≤ N 個 Run，不是全部。
  阻塞的影響也被關在一個容器裡。
- **代價**：需要一個調度層（哪個 Run 去哪個容器）與容器生命週期管理
  （閒置多久回收、健康檢查、重啟）。比 B 複雜，但比「無限開容器」可控。
- **否決 B 而選 C 的理由**：B 的失敗模式是「全有或全無」。
  一個 Agent 的容器掛掉，它的所有使用者同時失去服務，而且沒有任何降級空間。
  N 是一個可以調的旋鈕；「全部」不是。

## 決定：選項 C，`SANDBOX_RUNS_PER_CONTAINER = 30`

原提案建議 N=1（先把常駐化做對再調並發）。**使用者裁決直接用 30。**

這個數字的意義要講清楚，因為它是之後調參的基準：

> **N=30 表示一個容器內同時 30 個 Run 共用該容器的 2 GB，平均每 Run 約 68 MB。**

LLM agent 大部分時間在等 I/O，這通常夠用。**不夠的情況是具體的**：
agent 把大 payload（長文件、大 JSON、圖片）整份讀進記憶體時，
幾個並行就會吃掉整個額度，然後**同容器的 30 個一起被 OOM killer 帶走**。

因此：

- `N` 必須是**設定項**（`SANDBOX_RUNS_PER_CONTAINER`），不是常數 —— 要能依實測調
- 容器的 `mem_limit` 也要跟著可調；N 與記憶體是一組的，不能只調一個
- 監控要能看出「容器是被 OOM 殺的」還是「程式自己掛的」，否則調不動

### 派工方向：容器**拉**，平台不**推**

常駐容器要拿到工作，有兩種做法：

| | 平台推（容器開 port） | **容器拉（long-poll，採用）** |
|---|---|---|
| 網路方向 | 沙盒要接受 inbound | **維持只有 outbound 到 Gateway** |
| image 契約 | 要改：容器得開 HTTP port | **不變**（SPEC §8.1「容器內不開對外 HTTP port」保住） |
| L1 隔離 | 要放寬 | **一個字不動** |

**選拉的理由不是效能，是隔離。** 推的做法要求沙盒監聽連線，
那會讓 SPEC §8.1 與 L1 的「沙盒只有一個對外方向」失效 ——
而那正是 P4 最容易驗證的一條性質。拉的做法讓網路拓撲**完全不變**：
容器仍然只會主動打 Internal Gateway，只是多了一條 `long-poll 取工作` 的路徑。

## 對五條立場的影響

| | 影響 |
|---|---|
| **P1** 使用者程式碼不在平台行程內 | **不變。** 仍在獨立容器裡 |
| **P2** LangGraph | **不變** |
| **P3** API + MCP 雙門面 | **不變**（對外形狀完全一樣，使用者無感） |
| **P4** 沙盒拿不到長期憑證 | **立場不變，實作要改。** 見下 |
| **P5** 版本不可變 | **不變**，但容器綁定單一版本 —— 發新版要換容器（藍綠切換） |

### P4 怎麼保住

現在 run token 綁定單一 `run_id`、TTL = 該 Run 的 timeout、跑完撤銷。
常駐容器服務多個 Run，所以 **token 必須跟著工作項走，不能跟著容器走**：

- 容器啟動時**不帶任何 token**
- 每次派工把該 Run 的 token 一起送進去
- 容器內以 `contextvars` 綁定，確保 Run A 的 token 不會洩漏到 Run B 的 context

**這是把容器邊界免費給的東西改成靠程式碼寫對。** 因此：
Internal Gateway 的「token 屬於哪個 run」驗證**變得更重要**，不是更不重要 ——
它是這條路上唯一還由平台強制的檢查。

## 何時該重新檢討

- **要跑不可信的程式碼**：立刻回到選項 A。共用容器的隔離等級撐不住惡意程式碼，
  這是 ADR-0005「只跑信任的程式碼」前提的直接後果。
- **出現第二個租戶**：同上，而且更嚴重 —— 跨租戶狀態殘留正是 ADR-0001 第 2 條原本要防的。
- **實測顯示 `async def` 裡阻塞是常態而非例外**：那表示這個模型對使用者太難用對，
  應該退回 A 並用其他方式解決容量。
