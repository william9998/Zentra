# ADR-0016：同一個版號重新註冊 = 取代那個版本

| | |
|---|---|
| 狀態 | Accepted |
| 日期 | 2026-10-15 |
| 修改 | SPEC §2 P5 的字面、[ADR-0013](ADR-0013-hard-delete-agents-and-images.md)「沒有任何路徑可以單獨刪某一版的 image」 |

## 脈絡

原本同一個 `agent_id + semver` 第二次註冊回 `409 VERSION_CONFLICT`。結果是：

- 開發時每改一次就得換版號，`1.0.0`、`1.0.1`、`1.0.2`… 版號失去意義，變成計數器。
- 每個版號都留著一個 image，平台上的 image 只增不減（唯一的清理路徑是刪整個 Agent）。
- 驗證失敗（`BUILD_FAILED`）的版號也永遠不能再用。

**版號由開發者決定。** 開發者用同一個版號再送一次，意思就是「這個版號換成這個 image」。

## 決策

1. **同版號重新註冊 = 取代。** `POST /v1/agents/{id}/versions` 不再因為版號已存在而回 `409`。
   平台建一筆**新的** `BUILDING`，跟第一次註冊走同一條驗證路徑。
2. **驗證通過才換。** 新的那筆變成 `PUBLISHED` 的同一個交易裡，舊的 `PUBLISHED` 改成 **`SUPERSEDED`**。
   驗證失敗 → 新的那筆 `FAILED`，**舊的繼續服務**，REST / MCP 不會斷。
3. **舊紀錄保留，不原地改寫。** `SUPERSEDED` 那筆的 digest 一個字都不動，
   舊 Run 仍查得到當時跑的是哪個 image。`SUPERSEDED` 不出現在任何版本端點、不能被呼叫。
4. **舊 image 自動清掉。** 等到沒有未終結的 Run 還綁在舊的那筆上，worker 停掉舊容器、
   刪主機上的 image、刪內部 registry 的 manifest（跟 ADR-0013 同一套作法）。
   **其他還沒被取代的版本（任何 Agent）用同一個 digest 時不刪。**
5. **同版號同時只能有一個在 build。** 已經有一筆 `BUILDING` 時再送 → `409 VERSION_CONFLICT`。
6. **送來的 `image_ref` 跟現役的一模一樣 → 不重 build。** 直接回現役那筆（`202`，狀態 `PUBLISHED`）。

## P5 現在的意思

P5 要防的是「**發布過的東西在腳下被換掉**」—— 一個 Run 跑到一半、或查歷史時，發現 image 不是當初那個。
這件事仍然成立：

- 一筆版本紀錄的 digest 永遠不變（沒有 `UPDATE image_digest` 的路徑）。
- Run 在建立時就綁定那一筆，排隊中與執行中的 Run 跑完前，舊 image 不會被刪。
- 取代是**新增一筆 + 切換指向**，不是改寫。

改變的是「版號 → 哪一筆」這個對應，現在由開發者決定。
呼叫端用 `version: "1.0.0"` 固定版號，**拿到的是那個版號當下服務中的 image**。
要「永遠是同一個 image」的呼叫端，應該要求開發者換版號，平台不替他擋。

## 代價（誠實列出）

- **同一個版號在不同時間可能是不同的 image。** 看 Run 紀錄要看 digest，不要只看版號。
- **刪 manifest 不等於釋放空間。** blob 要跑 `registry garbage-collect` 才會真的消失（ADR-0009 的程序不變）。
  畫面上不可以說「已釋放空間」。
- **取代瞬間排隊中的 Run 跑的是舊 image。** 它們在建立時就綁定了舊的那筆，這是刻意的：
  不能讓一筆 Run 在建立後才換掉它要跑的程式。

## 不做

- **刪除單一版本。** 這次只做同版號取代。要刪就是另一個端點，需要另外決定。
- 原地改寫既有那一筆（會讓舊 Run 查不到當時跑的 image）。
